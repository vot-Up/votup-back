# ADR-003: Service Layer for Admin Actions with Error Handling

## Status
Accepted

## Date
2026-05-16

## Context
Admin custom actions (activate voting, close voting, activate plate) need to modify business data. The service layer already implements these operations with business rule validation. The question is whether admin actions should use the service layer or bypass it for direct ORM access.

## Decision
Admin actions call service layer functions directly. Errors (business rule violations, DoesNotExist) are caught and displayed to the admin via `self.message_user(..., level=ERROR)` with logging. Business rules are respected — if the service raises, the admin sees a clear error message.

## Alternatives Considered

### Alternative 1: Bypass Service Layer
- **Description**: Admin actions access ORM directly, skipping service validations
- **Pros**: Full freedom to edit data for verification purposes
- **Cons**: Bypasses business rules, could create inconsistent state, defeats the purpose of verification
- **Why rejected**: The admin's purpose is to verify the service layer works correctly — bypassing it would make verification meaningless

### Alternative 2: Hybrid — Try Service, Offer Force Bypass
- **Description**: Try service first, if it fails offer a "force" option to bypass
- **Pros**: Flexible — can verify both with and without business rules
- **Cons**: Complex UI, confusing UX, risk of accidental data corruption
- **Why rejected**: Over-engineering for this use case; if bypass is needed, raw SQL or shell is available

## Consequences

### Positive
- Admin behavior matches API behavior — consistent verification
- Service layer bugs surface in admin actions (the purpose of this feature)
- Error messages are user-friendly and logged for debugging

### Negative
- Admin cannot override business rules from the UI
- Service layer exceptions must be caught and handled gracefully

### Risks
- If service layer functions change signatures, admin actions break — mitigated by thin wrapper functions with clear error handling

## Implementation Notes
- Each action wraps service call in try/except
- Catch `ValidationError`, `DoesNotExist`, `PermissionDenied`, generic `Exception`
- Use `logging.getLogger(__name__)` for error logging
- Use `self.message_user(request, str(e), level=messages.ERROR)` for user feedback
